# Wave 6.1 — Authoring → Render Round-trip

## Verdict

**Gate 6.1: PASS_WITH_CONSTRAINTS**

The authoring state now crosses a narrow local runtime bridge into the existing
Wave 5 static renderer. The final PNG is generated by the same
`DocumentaryCard` tree used by the live preview, and runtime tuning remains
outside `StaticRenderManifest`. The constraint is that browser interaction
could not be completed in this checkout because the local environment has no
Supabase variables and the repository proxy runs for the dev route; the
browser inventory was also unavailable. The bridge, renderer, component
parity, and visual PNG evidence were verified directly.

## Objective and boundary

```text
AuthoringState
  → deriveManifestFromState()
  → AuthoringRenderRequest { manifest, overrides }
  → /dev/creative-preview/render (local-only bridge)
  → Wave 5 resolveStaticRenderManifest()
  → Remotion StaticRenderManifestStill
  → DocumentaryCard(previewTuning?)
  → PNG + execution metadata
```

No persistence, queue, worker, production render API, database, upload, or
video/timeline behavior was added. The request is a runtime authoring boundary,
not a domain contract and not a schema under `lib/schemas/creative`.

## Browser verification

The requested route was attempted at `http://localhost:3001/dev/creative-preview`.
The dev server was started once with output captured under the ignored `.tmp`
directory. The request failed before the page could render because the current
checkout has no `.env*` file and `proxy.ts` invokes Supabase session setup for
all matched routes:

```text
Your project's URL and Key are required to create a Supabase client!
```

No credentials were fabricated or written. `cua.getState()` also reported no
browser surfaces. Consequently, interactive checks (selectors, tuning sliders,
reset buttons, and the Render this click) are documented as **not browser
verified in this environment**, rather than claimed. The route remains a
static dev route in the build and the underlying render operation was exercised
through the same request/bridge code path.

The Wave 6 visual claims remain unchanged in code: cover/info, identities A/B,
4:5/9:16, live content/tuning, reset controls, debug panel, checkerboard alpha
indicators, and the direct `DocumentaryCard` preview tree are still present.

## AuthoringRenderRequest

`lib/creative/authoring/render-request.ts` defines the narrow runtime boundary:

```ts
type AuthoringRenderRequest = {
  manifest: StaticRenderManifest
  overrides?: {
    documentaryCard?: DocumentaryCardPreviewTuning
  }
}
```

Runtime validation is Zod-based and uses the existing `StaticRenderManifestSchema`
for the manifest plus bounded validation for the already-existing
`DocumentaryCardPreviewTuning` shape. Unknown request keys are rejected. The
request is not exported as a neutral creative schema or persisted entity.

## Manifest purity and overrides

`deriveManifestFromState()` continues to emit only semantic render input. Its
JSON contains no `tuning`, `previewTuning`, `debugPanelOpen`, `offsetX`,
`offsetY`, hero rotation/scale, or title tuning. The current tuning is attached
only as `overrides.documentaryCard` when the UI constructs the runtime request.

The Remotion adapter accepts an optional `overrides` field on
`StaticRenderManifestStillProps`. It passes the override to
`documentaryCardPropsFromResolvedInput()`, which passes it to the same
`DocumentaryCard` component. With no override, the prop is absent and Wave 5
behavior is preserved.

## Local development bridge

`app/dev/creative-preview/render/route.ts` is explicitly Node/local-only:

- production requests return 404;
- the browser sends only JSON data validated by `authoringRenderRequestSchema`;
- `child_process.spawn()` uses `process.execPath` and one repository-controlled
  runner path, with `shell: false`;
- no command, package command, executable, output path, or filename is accepted
  from the client;
- the runner generates the output directory and random identifier under
  `.tmp/creative/authoring-roundtrip/`;
- the response returns execution metadata and a data URL for the PNG, so the
  UI does not need to access an arbitrary filesystem path.

The runner (`scripts/creative/run-authoring-render.mjs` →
`render-authoring-request.ts`) calls the Wave 5 resolver and
`StaticRenderManifestStill` composition. This is a local proof, not a
production Remotion API.

## Render this and final result UI

The Authoring Lab header now has `Render this` with four explicit states:

- `idle` — no render requested;
- `rendering` — request in flight and button disabled;
- `success` — final PNG and metadata displayed;
- `error` — bridge error displayed without hiding the live preview.

The final render panel shows the PNG beside/below the live preview, duration,
variant, canvas, diagnostics count, output identifier, bridge identity, and
whether runtime tuning was included. The returned output path is technical
metadata only and is server-generated.

## Parity proof

The tuned scenario used cover A with:

```text
hero:  offsetX 42, offsetY -24, rotation 2, scale 1.08
title: offsetX 9,  offsetY 4,   rotation -1
```

The request rendered a real 1080×1350 PNG with `tuned: true`, empty
diagnostics, and `bridge: local-dev-only`. The default request rendered a
second 1080×1350 PNG with `tuned: false`. Full-size inspection showed the tuned
hero displaced/scaled/rotated relative to default while the paper/title
transformation and editorial content remained in the same component tree.

## Transparency proof

The render continues to use the Wave 5 material assets and their alpha-aware
URLs. Torn paper and tape remain RGBA assets; the archival hero remains an
intentionally opaque WebP. The default and tuned PNGs showed no white matte
introduced by the material transforms.
